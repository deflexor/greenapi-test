# Telegram Web Chat на GREEN-API

Минималистичный веб-мессенджер для обмена текстовыми сообщениями Telegram через
[GREEN-API](https://green-api.com/telegram/). Реализует реальную интеграцию с API:
проверку подключения, отправку текстовых сообщений, получение входящих через
long-polling и подтверждение уведомлений. Никакой имитации: все операции выполняются
настоящими запросами к GREEN-API.

## Технологический стек

- React 19 (функциональные компоненты, Hooks) + TypeScript (strict)
- Vite 7 — сборка и dev-сервер
- CSS Modules — локальная изоляция стилей
- Vitest 3 + React Testing Library — тесты
- ESLint 9 (typescript-eslint, react-hooks) + Prettier

Единственные runtime-зависимости — `react` и `react-dom`.

## Архитектура проекта

```text
src/
├── app/App.tsx                  # композиция: экран подключения ↔ экран чата
├── components/                  # UI-компоненты (только отображение и события)
│   ├── ConnectionForm/          #   ввод idInstance и apiTokenInstance
│   ├── ConnectionScreen/        #   экран подключения
│   ├── ChatScreen/              #   раскладка чата (список + переписка)
│   ├── ChatList/                #   список чатов
│   ├── ChatHeader/              #   заголовок текущего чата
│   ├── MessageList/             #   лента сообщений, автопрокрутка у низа
│   ├── MessageItem/             #   пузырь сообщения, статус, повтор
│   ├── MessageComposer/         #   ввод сообщения (Enter/Shift+Enter)
│   ├── NewChatForm/             #   открытие чата по идентификатору
│   └── StatusBadge/             #   индикатор состояния подключения
├── features/
│   ├── connection/              # useConnection: статусы disconnected|connecting|connected|error
│   └── chat/                    # useChats: чаты, отправка, цикл получения; chatModel (чистая логика)
├── services/greenApi/           # изоляция GREEN-API: client, telegram, types, errors
├── utils/                       # chatId, abort, format, random
├── styles/global.css            # CSS-переменные и базовые стили
└── test/                        # setup и тесты (Vitest + RTL)
```

Принципы: компоненты не делают HTTP-запросов; весь транспорт изолирован в
`services/greenApi`; бизнес-логика сообщений — чистые функции `chatModel` и
`notification`; состояние — локальные хуки (`useState`/`useReducer` не нужны,
глобальный стор не используется); ошибки API приводятся к типизированной
`ApiError` с безопасными для показа сообщениями.

## Настройка GREEN-API

1. В [личном кабинете](https://console.green-api.com) создайте инстанс
   Telegram-интеграции и привяжите к нему аккаунт Telegram (состояние инстанса
   должно стать `authorized`).
2. Убедитесь, что у инстанса **не задан `webhookUrl`** (приём работает через
   HTTP API; при заданном webhook-URL очередь уведомлений не отдаётся).
3. Возьмите из кабинета `idInstance` и `apiTokenInstance` и введите их на экране
   подключения.

Хост API вычисляется из `idInstance` по правилу документации
(`4100000000 → https://4100.api.green-api.com`); отдельный адрес вводить не нужно.

## Использование

1. Введите `idInstance` и `apiTokenInstance`, нажмите «Подключить» — выполняется
   реальный запрос `getStateInstance`.
2. Откройте чат:
   - chatId пользователя — положительное число, например `10000000`;
   - группа — число с минусом, например `-10000000000000`;
   - `@username` или телефон `+79991234567` — предварительно проверяются методом
     `checkAccount` и разрешаются в chatId.
3. Пишите сообщения: Enter — отправить, Shift+Enter — перенос строки. Статусы
   сообщений: ⏳ отправляется, ✓ принято GREEN-API, ⚠ ошибка (с кнопкой «Повторить»).
4. Входящие сообщения приходят автоматически (long-poll `receiveNotification`,
   подтверждение `deleteNotification`). Первое сообщение от нового собеседника
   само добавляет чат в список.

## Используемые методы GREEN-API (Telegram)

| Метод                       | Назначение                                                |
| --------------------------- | --------------------------------------------------------- |
| `GET getStateInstance`      | проверка подключения при входе (лимит 1 rps)              |
| `POST sendMessage`          | отправка текстового сообщения                             |
| `GET receiveNotification`   | long-poll одного уведомления из очереди                   |
| `DELETE deleteNotification` | подтверждение обработки уведомления                       |
| `POST checkAccount`         | проверка существования получателя по `@username`/телефону |

## Ограничения Telegram-интеграции

- **Истории сообщений нет.** API получения (`receiveNotification`) отдаёт только
  новые уведомления из очереди (хранятся 24 часа). Переписка накапливается с
  момента открытия приложения; журналы (`GetChatHistory`) не используются.
- **HTTP 200 от `sendMessage` — это приём сервером, не доставка.** В интерфейсе
  статус ✓ означает «принято GREEN-API». О недоставке (например, в сервисный чат)
  приложение узнать не может.
- **Идентификация получателя.** Telegram-интеграция оперирует числовым chatId;
  телефон или username — только через `checkAccount`. Если у пользователя скрыт
  номер/username настройками приватности (`exist: false`), открыть чат не
  получится — попросите собеседника написать первым: чат откроется автоматически.
- **Служебные и нетекстовые уведомления** (статусы, правки, реакции, медиа)
  подтверждаются и скрываются: приложение рассчитано на текстовые сообщения.
- **Лимиты частоты.** Превышение rps-лимитов возвращает 429/466; такие ошибки
  показываются, автоматических повторных отправок с неопределённым результатом нет.
- **Одно устройство получения.** Очередь уведомлений выдается одному потребителю;
  параллельный запуск второго приложения на том же инстансе будет забирать
  уведомления по очереди.

## Безопасность и работа с токеном

- `idInstance` и `apiTokenInstance` хранятся **только в памяти** (React state):
  ни localStorage, ни sessionStorage, ни URL, ни логи не используются.
- Токен никогда не попадает в сообщения об ошибках: транспортные ошибки
  заворачиваются в `ApiError` с фиксированным безопасным текстом, URL запроса
  (содержащий токен) не показывается.
- Все ответы API обрабатываются как недоверенные данные: тела уведомлений
  валидируются до использования, пользовательский текст рендерится без
  `dangerouslySetInnerHTML`.
- Запросы идут напрямую из браузера: GREEN-API разрешает CORS
  (`Access-Control-Allow-Origin: *`). Серверный посредник не требуется, но
  транспорт изолирован в `services/greenApi` и при необходимости переносится на
  backend без изменения UI.
- Помните: токен в браузерном приложении виден владельцу браузера (devtools,
  сетевые запросы). Для публичных деплоев используйте бэкенд-посредник и
  обновляйте `apiTokenInstance` в кабинете при компрометации.
